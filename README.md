# shikumin_zukai

仕組み図解のアーティファクトを、作るたびに Jev（TypeSafe AI の System One モデル）に採点させ、落ちた項目だけを直して回す環境。判定はすべて記録され、スマホから開けるパネルに同期される。

| 部品 | 実体 | 役割 |
| --- | --- | --- |
| `zukai-jev` MCP | `mcp/server.js` | 図解を Jev に送って 7 項目 + 2 ゲートで採点させる |
| ルーブリック | `mcp/rubric.js` | 図解固有の評価軸。`jev.rubric.json` を置けば差し替え |
| 記録 | `.jev/runs.jsonl` | 毎周の判定。唯一の真実 |
| パネル | [品質ゲートパネル](https://claude.ai/artifact/QU2JMRrKPk7uC5hkrBTsJf) | スマホから稼働状況と判定を見る（Artifact DB） |
| ループ手順 | `.claude/skills/zukai-loop/SKILL.md` | 生成 → 検査 → 修正 の回し方 |
| 図解の例 | `artifacts/jev-loop.html` | この一周そのものの図解 |

## 使い方

```bash
npm install
npm run check          # MCP ハンドシェイクから評価一周までの自己診断
```

### 1. Jev のキーを入れる

```bash
export TYPESAFE_API_KEY=...    # https://console.typesafe.ai
```

**キーが無い場合も動くが `stub` モードになる。** スコアは入力のハッシュから作った決定論的なダミーで、品質判断には一切使えない。`jev_ping` の `mode` と、パネル上の `STUB` バッジで常に見分けられるようにしてある。

### 2. MCP を読み込む

`.mcp.json` に登録済み。Claude Code をこのディレクトリで起動すれば `jev_*` ツールが生える。

| ツール | 用途 |
| --- | --- |
| `jev_ping` | live か stub か、どのルーブリックかを確認（最初に呼ぶ） |
| `jev_review` | 7 項目 + ゲートの本採点。`fixes` に直す対象が返る |
| `jev_gate` | 「出せるか」だけを見る軽量版 |
| `jev_decide` | 任意の型付き質問を素で投げる |
| `jev_feed` | 未同期のレコードを取り出す（パネル同期用） |
| `jev_status` | 稼働状況と直近ランの要約 |

### 3. 回す

「〜の仕組みを図解にして」と頼めば `zukai-loop` スキルが起動し、生成 → `jev_review` → 修正 → 再採点を最大 3 周する。

### 4. スマホで見る

Claude が毎周 `jev_feed` の結果をパネルの DB に書き込む。スマホで上のリンクを開けば、検査中／待機中、総合スコア、項目別の落ち、反復ごとの推移が出る。

## ルーブリック

| 項目 | 見るところ | 必須 |
| --- | --- | --- |
| 構造の正確さ | 要素の分け方・階層が仕組みを写しているか | ✓ |
| 因果と流れ | 矢印と順序が曖昧でないか | ✓ |
| 情報密度 | 1 枚で処理できる量か | |
| 視覚階層 | 重要な要素が最初に目に入るか | |
| ラベルの具体性 | 「最適化」等の一般論語になっていないか | ✓ |
| 自己完結性 | 口頭説明なしで理解できるか | |
| 可読性 | スマホ幅・ライト/ダーク両方で読めるか | |
| 裏付け（ゲート） | 元資料にない断定が混じっていないか | ✓ |
| 公開可否（ゲート） | このまま社外に出せるか | |

必須項目が閾値（正規化 0.7）を割ると `block`＝差し戻し。必須以外だけなら `revise`。全通過で `ship`。

## 確認済みのこと / 未確認のこと

事実と推測を分けておく。

**確認済み**
- MCP の往復（ハンドシェイク、6 ツール、評価 → 記録 → フィード → カーソル前進、リポジトリ外パスの拒否）は `npm run check` の 25 項目で通っている。
- 記録 → Artifact DB → パネル表示の経路は、`artifacts/jev-loop.html` を実際に 1 周させて確認済み（stub モード）。

**未確認（実キーが要る）**
- Jev のエンドポイント・認証・リクエスト形式は参照実装 `codaaiteam/jev-mcp` の実装から取った。確信度は高いが、**実キーでの疎通は未実施**。
- `score` の戻り値が 0 起点か 1 起点かは公開資料から確定できなかった。`mcp/jev.js` の `normalizeScore` で両方を受けて 0〜1 に正規化している。実キーが入ったら、既知の入力で端の値を一度確かめること。
- 課金・`usage` フィールドの形も未確認。

**前提が崩れる条件**
- Jev 側が `questions` のスキーマやレスポンス形状を変えれば `mcp/jev.js` と `mcp/rubric.js` の解釈が壊れる。壊れた場合 `interpret` は `verdict: "unknown"` を返す設計なので、誤って `ship` にはならない。
- ルーブリックの閾値 0.7 は根拠のある値ではなく初期値。実キーで数周回して調整する前提。
