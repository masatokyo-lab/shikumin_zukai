# 生成 → Jev 検査 → 不合格なら修正 / 合格なら出荷判定へ

生成したら必ず検査する。検査せずに「できました」と言わない。
検査器の出力は **合格（pass）/ 不合格（fail）の2値**。出荷するかどうかは Jev ではなく**ユーザーが決める**。

設計の契約は `docs/HANDOFF-jev-gate.md`。この手順とそれが食い違ったら HANDOFF を正とする。

## 0. モードと基準を最初に確かめる

`jev_ping` を呼ぶ。`rubrics` に diagram（22問）と article（18問）の両方が返る。
`mode` が `stub` なら **スコアはダミー** なので、ユーザーに一行で伝える:

> Jev の APIキーが未設定のため stub モードです。以下の判定は品質判断には使えません。

`live` でも、`warnings` に較正前の警告が出ている間は**この判定を品質の根拠として語らない**。
落ちた項目を直す材料としては使ってよいが、「Jev が通したから良い」とは言えない。

## 1. 図解を作る

- 出力先は `artifacts/<slug>.html`。単一 HTML、インライン SVG、外部依存なし。
- ライト/ダーク両対応、スマホ幅で読めること。**これはルーブリックでは検査されない**
  （Drive 正本に対応する質問が無い）。自分で確認すること。
- **図は SVG ソースとしてテキストで渡る。** PNG/JPEG は Jev が評価できないので使わない。
- Artifact として公開する場合は `artifact-design` スキルを先に読む。

## 2. `jev_review` で検査する

```
jev_review({ task, artifact_path, scope, source_material, note })
```

- `scope` は対象の種類。図を含むなら `diagram`（既定、22問）、図を伴わない文章なら `article`（18問）。
  **取り違えると、図の無い文章に軸・単位の質問を当てて空振りする。** 迷ったら図が1つでもあれば `diagram`。
- `task` は依頼内容そのまま。`source_material` は元資料。**これを省くと裏付け判定（`g5_*`）が効かない。**
- **返る `result` は `pass` / `fail` の2値。次にやることは `next_action` に入っている**（下の表）。
  内訳の `verdict`（`ship` / `revise` / `block` / `unknown`）は記録用。`revise`（群FAIL は無いが単発の欠陥がある）は合格。

| `next_action` | 意味 | やること |
|---|---|---|
| `fix_and_rereview` | 不合格（群FAIL） | 3 に従って直し、再検査 |
| `stop_and_escalate` | 不合格で、回しても直らない（反復の上限・停滞・振動）か、判定不能 | **直さずに止めて**ユーザーに返す（4） |
| `hand_to_human` | 合格 | 5 に従って出荷判定をユーザーに渡す |

- **`probability` は「欠陥が存在する確率」。高いほど悪い。** 逆に読まないこと。
- `groups` に群ごとの FAIL、`fixes` に落ちた項目とそれが何を見ているかが入る。
- `escalate` が空でなければ、**直さずに止めて人間に返す**（4 参照）。
- `unreachable_groups` / `fragile_groups` は「構造上ほぼ落ちない群」。ここが出ている間、
  その群は検査されていないに等しい。通ったことを根拠にしないこと。

判定不能（`fail_reason: "unknown"`、`missing_answers` が空でない）は不合格として返る。**直す対象が無いので回さずに人間に返す。**
回答が欠けたまま進むと群の欠陥数が実際より少なく数えられ、静かにゲートが緩む。

## 3. 直す

`fixes` のうち `blocking: true`（群がFAILしている項目）から先に直す。それ以外はその後。

- `g5_*`（無標の推測、出典なき具体性、出典粒度の不一致、結論の誇張）が立った場合、それは
  **「出典を確認せよ」という指示であり「間違っている」という判定ではない。**
  Jev は事実の真偽を検証できない。確認は自分かウェブ検索で行う（`fixes[].means` に同じ注記が入る）。
- 群の判定を無視して進めてはいけない（HANDOFF 禁止事項 #1）。
- `s7_originality` の判定を自分で上書きしてよいが、**上書きしたら必ず理由を書いてユーザーに見せる。**
  黙ったオーバーライドは禁止。

直したら `note` に変更点を書いて再度 `jev_review`。`run_id` は自動で引き継がれ、`iteration` が増える。

**欠陥が前周より増えたら、その変更は捨てて前の版に戻す。** 反復は単調改善でなければ意味がない。

## 4. 止めどき（不合格のまま止める）

**止めどきは `jev_review` が `escalate` に入れて返す（`next_action: stop_and_escalate`）。自分で履歴を突き合わせない。**
空でなければ**即座に止めて人間に返す**。`escalation_reasons` にそのまま使える理由文が入っている。

| トリガー | 意味 |
|---|---|
| `retry_limit` | 反復が上限（3周）に達した |
| `stagnation` | FAIL群の集合が前周と同一。同じ場所を叩き続けている |
| `oscillation` | 前周になかった群がFAILした。**総数が減っていても止める** |

`oscillation` は項目間のトレードオフ（具体性↑で密度↓など）をモグラ叩きしている状態。
回し続けても収束しないので、ルーブリックが合っていないか元資料が足りない。どちらかを述べて判断を仰ぐ。

判定は**群単位**で行われている（項目単位だと誤検出で毎回集合が変わり常時発火する）。
一方、修正指示に使うのは項目単位の ID。この二つを混同しないこと。

群は scope で変わる。diagram は g1 トレーサビリティ / g2 図のタイトル・軸・単位 /
g3 本文と図の整合 / g4 粒度バランス / g5 事実と推測の区別。
article は g1 / g4 / g5 / g6 記事としての構成。**同じ run の途中で scope を変えないこと**
（群の集合が変わるので前周と比較できなくなり、サーバーは比較を打ち切る）。

判定不能（`fail_reason: "unknown"`）も即座に止める（2 参照）。

## 5. 合格したら出荷判定をユーザーに渡す

合格は「群単位の欠陥が見つからなかった」であって、出荷してよいという判定ではない。**出荷するかはユーザーが決める。**
次の3つを見せて止まる:

1. **合格したこと**（`result: pass`。stub なら「ダミー判定」、較正前なら「閾値は暫定」と必ず添える）
2. **`s7_originality` の人間確認**（`human_review`）。一次経験の裏打ちは Jev の死角で、もっともらしい記述を
   生成すれば通過できてしまう（HANDOFF 禁止事項 #3）
3. **参考として残った単発の欠陥**（`fixes` のうち `blocking: false`）。特に `g5_*` は「出典を確認せよ」として先頭に出す

ユーザーが出荷判定を報告したら、`jev_label` で記録する:

```
jev_label({ seq, human_verdict: "pass"(出荷する) | "fail"(出荷しない), note?, group_labels? })
```

- **ユーザーが言った値だけを渡す。** 推測で埋めない。報告が無ければ記録しない
- 返った `sample`（本文つき）は Drive「99. Jev連携/labels」に `<id>.json` で保存する。
  **このリポジトリは public なので、本文をリポジトリに書かない**
- `labels/ledger.jsonl`（本文なし）は commit / push する。クラウドのコンテナは消える
- 「Jev は合格、ユーザーは出荷しない」は見逃しの候補。理由を `note` に残してもらう（較正で原因を追うため）

## 6. 毎周ダッシュボードへ同期する

検査のたびに、スマホから見えるダッシュボードへ反映する。これをやらないと「Jev が動いているのが見える」
状態にならない。

1. `jev_feed({ since_seq })` を呼ぶ（初回は `0`、以降は前回の `next_since_seq`）。
2. 返った `records` を `ArtifactData` の `batch` で 1 回にまとめて書く:
   - collection `evals`、`doc_id` は `String(seq)`、中身はレコードそのまま。
   - collection `status`、`doc_id` は `"current"`、中身は `state` に `mode` / `model` / `synced_at` を足したもの。
3. パネルの URL は README.md の表にある（`.jev/dashboard-url.txt` にも控えてある）。無ければ
   `dashboard/index.html` を `capabilities: {db: {}}` 付きで publish し、URL を両方に書いてユーザーに渡す。

`status` は毎回上書きする — これがスマホ側の「稼働中 / 待機中」表示になる。

## 禁止

- stub モードの判定を根拠に品質を語ること。
- 較正前の閾値による判定を「Jev が通した」として品質の根拠にすること。
- 検査を飛ばして完成を報告すること。
- `s7_originality` の人間確認を飛ばして完成を報告すること。
- 合格を「出荷してよい」と言い換えること。出荷判定はユーザーがする。
- ユーザーが報告していない出荷判定を `jev_label` に記録すること。
- `jev_label` の `sample`（本文つき）をリポジトリに書くこと。
- 群の判定を黙って無視すること。オーバーライドは s7 のみ、かつ理由を明示して。
- 判定不能（`unknown` / `missing_answers`）を通過扱いにすること。
- `escalate` が返っているのに回し続けること。止めどきの判定はサーバーが済ませてある。
- `jev_decide` に「公開してよいか」型の質問を投げること。`jev_gate` を消したのと同じ理由。
- ルーブリックに通すためだけに図解から情報を削ること（`g4_*` の欠陥は消えるが
  `g3_figure_not_supporting` が立つ。立たなければ検査が甘い）。
- `scope` を「通りやすいほう」で選ぶこと。図があるのに `article` を選べば g2 / g3 の
  22問中11問が丸ごと外れる。サーバーは内容から図の有無を判定していないので止められない。
- 「公開してよいか」を Jev に訊くこと。この環境はその判定をしない（HANDOFF 禁止事項 #4）。
